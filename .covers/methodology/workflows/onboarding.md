One safer retry is per helper-failure class across the phase, not per file.

Never clone/update the toolkit, reuse a previous target path, install target dependencies, execute target code or cross an external-service boundary implicitly.

Phase 0 apply installs only immutable nonconflicting toolkit assets. Continue with the already-loaded skill while treating copied methodology as project-pinned authority. SPEC-TOOL-030/R3-R4: verify a cold catalog with the optional fresh-process recipe in skill-discovery.md, or fully exit and relaunch Codex from the target. The probe does not activate newly copied skills in the current session; restart that session before claiming it can invoke them. The Full onboarding/master spec or Lite quick spec precedes project-specific setup or implementation changes. Reconcile existing steering/specs, save the reviewed overview and cold dry-run scorecard at the standard review paths (or recorded equivalents), and preserve team-local `AGENTS.md`, `.agents/skills` and `.covers` artifacts. The installed plugin starts the workflow; project-local artifacts remain the continuing team authority. Other contributors do not need the personal plugin.

Batch approval-bearing work into at most one request per class per phase: read-only discovery, isolated COVERS parser installation, COVERS evidence writes and COVERS metadata verification. A denial or repeated equivalent prompt stops that class. Never locate or invoke internal patch utilities, use undocumented substitutes or broaden sandbox access to complete administrative evidence. After local skills are installed, use a genuinely fresh process for catalog evidence; do not describe an in-process refresh as a cold handoff. Record fresh catalog discovery, current-session activation and tool health separately. On a supported-helper failure, retry once only when materially safer, then leave evidence pending and use `scaffolding/onboarding-handoff.md`. Preserve the exact error and do not infer its cause.

## Onboarding decisions: steering and existing specs

Before adoption, inventory root/nested agent steering and existing spec systems, including non-COVERS directories. Record owners where known, purpose, status evidence, references and overlapping scope. Choose and record a disposition: retain/coexist (preserve and link legacy records), integrate/bridge (retain the existing authority with explicit mappings), or migrate (separately scoped conversion with reviewed ID/path mappings and preserved history). Do not force migration merely to adopt COVERS. Define one governing source per scope and resolve conflicts before implementation; a reference alone does not establish compatibility. Do not invent completion status, IDs, approvals or code-coverage evidence from legacy metadata. The current CLI indexes only COVERS lifecycle directories; bridging another system requires reviewed work, not an assumption that it is indexed.

A `.git` directory is not an onboarding prerequisite. For a pre-source-control project, use a dated filesystem-snapshot identity and continue non-Git COVERS checks. Mark revision, branch, dirty state, baseline comparison and drift unavailable. Do not initialize Git or create a baseline commit without separate user authorization. Recommend source control as a later provenance improvement without blocking architecture discovery, specs, metadata checks or testing plans.

Under authorized onboarding, create a project-specific root AGENTS.md if no applicable root file exists. First check case variants, ancestor/nested instructions, override conventions and symlinks; do not create a competing file or follow a redirect blindly. If guidance exists, preserve it and deliberately merge the COVERS additions, resolving conflicts. Reference the shared contract, governing specs/catalog, existing-spec disposition, execution boundaries, and verified versus unverified commands. Record the decision and review owner in the onboarding record. CLI init supplies a proposal only; the onboarding agent performs the reviewed project-specific creation/merge. Copying the template without adapting it is not completion, and spec-only requests do not authorize application or guidance changes.

Verify the resulting steering file exists, its local links resolve, existing instructions/history survive, and the selected agent's fresh catalog discovers the intended repository skills before claiming that discovery checkpoint passed. If the governing onboarding record also requires current-session activation, keep that obligation pending until separately observed; a catalog probe cannot satisfy it. If required discovery or selected setup checks have not been tested, report partial onboarding rather than a pass. Application runtime and E2E may be explicitly outside this setup scope; mark them unverified without requiring their execution to complete onboarding.

## First testing signal and demonstration scope

After setup, recommend a unit-first baseline for a bounded simple-project assessment or demonstration. This testing-depth choice is independent of Lite/Full. Record the choice once in the existing overview/spec, honor an explicit preference, and ask only if broader scope is materially necessary. Follow workflows/testing.md and adapt scaffolding/baseline.md before authorized execution. Do not turn a request to onboard into automatic browser-tool installation or application execution.

Deliver a concise overview, the selected fast checks with actual outcomes, and a consolidated findings/decision list. Broader integration and E2E can be owned deferrals, not fake passes. A meeting may continue from stakeholder decisions to a bounded repair spec and failing-then-passing regression evidence without waiting for unrelated browser infrastructure. Browser-specific defects still need a faithful browser check before being claimed fixed; otherwise leave that finding for the later stage. Preserve all existing required gates and completed records.

## Discovered architecture checkpoint — SPEC-TOOL-022/R1-R3

Create an evidence-backed view of the **current architecture** during initial assessment: system context, components and ownership, data/control flows, persistence, integrations, authentication/authorization and trust boundaries, runtime/deployment, build/test/observability topology, and explicit sampled or unknown areas. Label claims observed, source-confirmed, inferred, claimed-only or unknown. Keep **target architecture** and recommendations separate so desired design is never reported as current implementation.

Adapt `scaffolding/wiki/architecture.md` as standalone Markdown or, when an authorized project wiki exists, as `wiki/pages/architecture.md` with registered source revisions and an index link. A diagram is optional and requires a text equivalent. Do not create a wiki automatically, require a diagramming product, or treat the untouched template as evidence.

## Dependency advisory checkpoint — SPEC-TOOL-020/R1

Inventory exact versions across the direct and transitive locked graph with an ecosystem-maintained package manager or parser. Before an external advisory query, classify public, private/internal and unknown packages; document the destination, exact metadata payload and privacy risk; and obtain actual authorization. Never send source, lockfiles, private package names or URLs, credentials or repository identity without specific authority. An offline/local advisory database or approved organization scanner is equally valid.

Preserve provider/date, package-version count, query errors, affected records and unique advisory IDs. Use authoritative details to assess affected ranges, withdrawn status, prerequisites, platform, runtime/build/development role, reachability and containment. A match is not automatically exploitable, and no match is not security clearance. Record a sanitized summary in the security register; keep sensitive detail access-controlled. Do not auto-upgrade: remediation requires a separate covering spec, locked dependency diff and proportionate tests.
