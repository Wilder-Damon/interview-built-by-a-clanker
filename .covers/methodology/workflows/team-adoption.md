## Team adoption and maintenance

SPEC-TOOL-011/R1,R3: use methodology/readiness.md to evaluate COVERS through reproducible onboarding, requirement fidelity, meaningful tests, challenged gates, cold team handoffs, operational safety and measured multi-project outcomes. Record evidence and gaps per dimension; do not average away a failed safety gate or claim a universal ten-out-of-ten method from one pilot. Improve demonstrated friction with minimal tooling. Distinguish methodology readiness, project release readiness and a spec critique score.

Keep the core minimal: skills, agent steering, plain-text specs/catalogs and a small local validator. Node and the pinned YAML parser support the CLI; Git is needed only for diff-based checks. Reuse project test tools. Do not add databases, services, global packages, browser runners, MCP connections or project agents merely because onboarding can install them. Project-specific agents require a scoped role, allowed tools/data, handoff/evidence contract and an authorization boundary; they do not inherit unrestricted authority.

At scale, search the registry by ID/domain/status/decision text with bounded pages before opening full specs. Rebuild the index from authoritative headers, validate freshness before execution, and preserve historical IDs. Concurrent authors merge their Markdown changes then regenerate the registry; do not treat JSON merge conflicts as permission to drop records. No daemon or external search database is needed for the initial toolkit.

Onboard with source/revision and steering inventory, architecture map, execution boundary, reviewed skills provenance, tool/version matrix, actual smoke/baseline results, candidate invariants and first slices. Prefer pinned local tools. Record environment variable names, never secrets. Reconcile AGENTS.md manually and validate the actual agent's skill discovery. Updating a personal skill is not silently authorized by project adoption.

Assign human owners to specs, critical invariants, tooling and release decisions. Use normal code review for guidance and tests as well as production code. Teams configure CI and protected branches deliberately; this distribution supplies a CI example but does not enable protection remotely. Record exemptions with owner, rationale and expiry/revisit date. Keep ownership rules compatible with existing governance.

Release readiness also includes operational fit: observability, rollback, recovery drills, data migration and incident feedback where relevant. Products that use AI need task-quality evaluations, prompt/model versioning, injection resistance, latency/cost and nondeterministic failure analysis in their own specs. These are not supplied by ordinary code coverage.

Toolkit version 0.6.6 is a pilot release. A reviewed Codex plugin can initiate onboarding, but committed project-local guidance and skills remain the shared team mechanism. On Windows, follow windows-onboarding.md for the read-only ownership preflight and scoped approved preparation/recovery before apply; ownership does not establish effective write permission. SPEC-TOOL-030: the optional skill-discovery.md fresh-process probe verifies exact enabled repository paths, not current-session reload or command-helper health. Fully restart the agent process before claiming that session can invoke newly copied skills, and preserve partial handoffs instead of bypassing failed supported tooling. Validate adoption in a disposable clone, review generated changes, then commit to the team's repository. Distribution contains no commercial promises or chosen license; establish distribution/reuse terms before external rollout.
